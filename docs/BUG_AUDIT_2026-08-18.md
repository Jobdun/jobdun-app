## Sam's reported bugs — root causes

### S1 — Licence verify shows an error — **CONFIRMED (client-side); three ranked candidates, all real defects**

**Framing fact:** licence auto-verify is dead code in 1.0.0+5 — `wizard_licence_step.dart:33` `_supportedStates = []` means the VERIFY button never renders, and `verification_wizard_page.dart:221-225` routes every trade to `_TradeCredentialsStep`; the client **cannot call `verify-licence` at all**. So Sam's error came from the manual-upload path or the receipts card:

1. **(Most likely) False "Verify your phone number first" block.** `manual_upload_sheet.dart:146-152` gates UPLOAD on `profileControllerProvider.…isPhoneVerified` — but `ProfileController.build()` never self-loads (`profile_provider.dart:66-73`); only Home/Profile pages hydrate it. Arrive via the Jobs-page nudge banner, the profile "ADD NOW" → `/verification` path, or a deep link, and `profile == null` → a phone-verified tradie is told to verify their phone; the CTA pushes `/profile/verify-phone`, which dead-ends for already-verified users (`phone_auth_page.dart:100`).
2. **Raw error bodies rendered as UI copy.** Non-2xx from the edge functions surfaces verbatim: `verifications_remote_datasource.dart:108-111` → `wizard_abn_step.dart:70-73` / `wizard_licence_step.dart:93-97`. Live-probed on prod: an expired/invalid session renders literally `Edge function verify-abn failed: {error: unauthenticated}`. 429s leak an ISO timestamp; 500 `db_error` echoes the Postgres message.
3. **"Opening the licence area" prints the raw exception object** — `verification_receipts.dart:80-90` renders `sub: '$e'` under "Couldn't load verification status" (shown on `profile_page_trade.dart:78` and the credentials hub). Concrete trigger: `verification_wizard_page.dart:223` passes `currentUserIdSync ?? ''` → `.eq('user_id','')` → Postgres `invalid input syntax for type uuid: ""` shown to the user. **This matches Sam's "when he went into the licence area something come up as well."**

**Ruled out with live probes:** function not deployed (both return their own handler bodies on prod), boot/env failure, ABR upstream (healthy JSONP with prod GUID), advisor-hardening grant revocation, CORS/verify_jwt. No licence-API secret is missing because **no real regulator call exists** — `nsw_adapter.ts:23-47` is a dev stub and `AUTO_VERIFY_ENABLED=false` is the only thing preventing stub licence numbers (`*00000`) from minting fake verified rows.
**To pin which one Sam hit:** get his screenshot (he sent them to Ken's WhatsApp); all three get fixed regardless.

**Client-side failure UX (must fix even after funding):**

### S3 — Keyboard won't dismiss — **CONFIRMED, systemic (iOS-heavy)**

**Root cause:** the app has no keyboard-dismiss strategy at all. Verified app-wide: `keyboardDismissBehavior` — 0 occurrences; page-level tap-outside unfocus — exactly 1 (`login_page.dart:110-112`); no app-level dismiss wrapper (`lib/app/app.dart:44-48` only clamps text scaling). Flutter's tap-outside default is a no-op on iOS/Android touch, multiline fields turn the return key into newline, and iOS number/phone pads have **no return key** — so any screen relying on "done" with a numeric field is a trap on iOS. Android self-heals via system back; iOS does not → Sam is on iOS.

**Worst instances (all cited by the sweep):**
| Screen | Mechanism | Symptom |
|---|---|---|
| `job_create_page.dart:382-467` | multiline description (newline key) + number rate field (no return key on iOS), scroll view `:345` has no dismiss | keyboard covers PRICING/URGENT/**POST JOB**; no way out — best match for Sam's report |
| `about_edit_page.dart:163-173` | text field fills the whole scroll view — nothing to tap, nothing to drag | total trap; only SAVE or discard-changes escape |
| `message_thread_input.dart:61-75` | `maxLines:null` makes `onSubmitted` dead — return key inserts newline, never sends | return key "broken"; keyboard stuck over thread; `message_thread_page.dart:361` list can't dismiss on scroll |
| `job_apply_sheet.dart:89-124` | number + multiline in a drag-to-dismiss modal | only downward gesture **closes the sheet and loses the draft** |
| `quote_respond_sheet.dart:110-131`, `review_compose_sheet.dart:144-152`, `report_sheet.dart:114-137`, `manual_upload_form.dart:204-215` | same modal-sheet pattern | keyboard covers SUBMIT; drag = data loss |
| `wizard_abn_step.dart:124-131` | 11-digit number pad, CTA pinned bottom | can't reach VERIFY — **gates job posting** (`job_create_page.dart:94-103`) |
| `phone_auth_steps.dart:118-122` | `TextInputType.phone` pad has no return key so `done`/`onSubmitted` unreachable | keyboard covers CONTINUE on phone sign-in |
| `rates_sheet.dart:101-125`, `trade_details_sheet.dart:149-160`, `business_details_sheet.dart:137-172` | numeric fields in `EditSheetScaffold` (no dismiss, `:95`) | keyboard covers SAVE (`edit_sheet_scaffold.dart:112`) |
| `job_location_field.dart:91-101`, `profile_location_field.dart:181-186` | postcode uses `textInputAction.next` on the **last** field | focus hops instead of closing (legacy no-MapTiler branch only) |

**Fix shape (S effort, high leverage):** add tap-outside unfocus (copy `login_page.dart:110-112`) into `EditSheetScaffold` + `BottomActionBar` + an app-level wrapper in `app.dart:44`, and `keyboardDismissBehavior: onDrag` on the six scrollables listed above; give multiline fields a toolbar Done or convert the chat return key to send. `about_edit_page` specifically needs the scroll-drag behavior (field occupies all tappable space).

### S4 — Role picker has no way back — **CONFIRMED, and it's FTUE slide 3, not /register**

The screen with "I'M HIRING / I'M LOOKING FOR WORK" cards that traps users is **FTUE slide 3** (`ftue_page.dart`). Mechanism — all three escapes are off at once for a login-originated user, and the stack is empty:
- `ftue_page.dart:157` — `showBack = widget.fromLogin && _currentSlide == 0` → back caret exists **only on slide 1**;
- `ftue_page.dart:165` — `showSkip: !isFinalSlide` → SKIP hidden on the role slide;
- `ftue_page.dart:181` — `onLoginLink: widget.fromLogin ? null : _onLoginLink` → the "I already have an account · LOG IN" escape is removed **exactly for users who came from /login** ("Create account" does `context.go('/ftue?from=login')`, `login_page.dart:90`);
- entered via `context.go` everywhere (also router redirect `app_router.dart:94`) → `canPop()` false → **Android system back exits the app**; no PopScope, no iOS swipe-back.
Only exits: pick a role, Google SSO, or "BROWSE OPEN JOBS". Swiping back through the PageView still works but has zero affordance. (`/register` step 1 does have a back caret → `context.go('/login')`, `register_page.dart:136-157`; still RISKY — system back exits app since it's always entered with `go`, and guests get bounced to the login wall instead of back to `/browse`, `register_page.dart:141-145`.)
**Fix shape (S):** show back+SKIP on all slides (or keep SKIP and make back visible whenever `fromLogin`), restore the LOG IN link for `from=login`, and add a PopScope that steps back a slide before letting the pop through.

### S6 — Profile photo from camera never uploads — **CONFIRMED: camera errors silently discarded (pick phase), upload chain itself is fine**

**Primary root cause:** `identity_sheet.dart:77-87` wraps `ImageUploadService.pickCropCompress` in `on UploadGuardException` **only**. The camera-exclusive failures image_picker actually throws — `PlatformException(camera_access_denied)` (iOS permission), `no_available_camera`, `already_active` (double-tap) — escape that catch, and because `_pickAvatar` is invoked as a discarded `VoidCallback` (`identity_sheet.dart:166`) the error goes to Sentry with **zero UI effect**: no camera, no spinner, no message. Gallery works because iOS PHPicker needs no permission and never throws — exactly Sam's "photo doesn't upload but gallery does" asymmetry.
**Secondary:** Android activity-death recovery is never wired — `ImagePicker.retrieveLostData()` / `ImageCropper.recoverImage()` have 0 uses in `lib/` (cropper docs require it) → on low-RAM Android the captured photo simply vanishes. **Contributing:** the whole `pickCropCompress` pipeline (`image_upload_service.dart:102-155`) has no try/catch and conflates "user cancelled" with real failures (`null` for both); compress throw is unguarded.
**Ruled out with evidence:** Info.plist purpose strings present (`ios/Runner/Info.plist:61-64`); Android manifest correct; storage RLS path `{uid}/avatar.jpg` matches policy (`rls.sql:375`); cache-busting works (`profile_remote_datasource.dart:210-211`); HEIC not implicated (cropper normalises to JPEG first).
**Device repro to split primary vs secondary:** deny camera permission → tap "Take photo" (camera never opens, nothing happens = primary); "Don't keep activities" on Android → photo taken then vanishes (= secondary).
